# ТЗ: Backend «Соцсеть» — Спринт 2 (Concurrency, Worker Pool, Tests, pprof)

## 1. Цель спринта

Сделать обработку лайков устойчивой под конкурентной нагрузкой: bounded-очередь команд, worker pool на goroutines/channels, корректная остановка воркеров, тесты с `-race`, бенчмарки и профилирование `pprof`.

- Основная точка изменений: существующий эндпойнт лайков  
  `POST /api/v1/posts/{id}/like`

## 3. Задача A: Лайки через очередь команд и worker pool

### 3.1. Общая идея

Обработка лайка должна происходить не “внутри хендлера напрямую”, а через постановку команды в **очередь** и выполнение команд воркерами.

### 3.2. Команда лайка

Внутри приложения лайк должен быть описан как команда `LikeCommand` с простыми полями (без зависимостей от `gin`/`net/http`):

Минимальные поля:
- `commandID` — строка/uuid (уникальный идентификатор команды)
- `postID`
- `userID`
- `createdAt` — время создания команды (или timestamp)

Дополнительно по желанию:
- `correlationID` / `requestID` — строка

### 3.3. Требования к очереди и воркерам

1. Очередь должна быть **bounded** (буфер фиксированного размера).
2. Должен быть worker pool из **N воркеров** (goroutines), которые читают команды из очереди и выполняют их.
3. Должен быть механизм корректного завершения:
   - `Start()` / `Stop(ctx)` (или `Run(ctx)`),
   - после остановки воркеры не должны “висеть” (без утечек goroutines),
   - после остановки новые команды должны корректно отвергаться (ошибка).
4. Бизнес-операция выполнения лайка должна быть отделена от доставки команды:
   - воркер получает `LikeCommand` и вызывает отдельный метод/функцию вида `ApplyLike(cmd) -> LikeResult`.

---

## 4. Задача B: Поведение существующего эндпойнта лайков (без изменения API)

Эндпойнт остаётся тем же: `POST /api/v1/posts/{id}/like`

### 4.1. Обязательное поведение

1. Хендлер формирует `LikeCommand` и пытается поставить команду в очередь.
2. Хендлер должен дождаться результата выполнения команды и вернуть ответ клиенту (механизм ожидания — на усмотрение реализации).
3. Если контекст запроса отменён (`ctx.Done()`), хендлер не должен зависать и должен корректно завершиться.

Переводим лайки на очередь + worker pool, чтобы ограничить максимальное число одновременно выполняемых операций и получить контролируемое поведение при пиках: запрос либо попадает в очередь и обрабатывается воркером, либо быстро получает “перегруз/нет места”, вместо того чтобы порождать неограниченную конкуренцию в обработчике.

### 4.2. Идемпотентность и потокобезопасность

- Если пользователь уже лайкал этот пост — повторный лайк **не изменяет** состояние (счётчик не растёт).
- Под конкурентными запросами (много goroutines) состояние остаётся корректным.
- Проект должен проходить `go test -race ./...`.

### 4.3. Результат выполнения команды

Результат выполнения должен быть представлен структурой `LikeResult` (формат на усмотрение)

## 6. Бенчмарки и профилирование (обязательно)

### 6.1. Benchmarks

Добавить несколько бенчмарков (пример):
- `BenchmarkLike_Direct` — выполнение лайка без очереди (напрямую, как “базовая линия”)
- `BenchmarkLike_QueueWorkerPool` — выполнение лайка через очередь + воркеры

### 6.2. pprof

Снимите профиль, чтобы понять, где тратится CPU/память в обработке лайков. 

**CPU-профиль:**
1) Запуск (пример):  
`go test ./... -run=^$ -bench=BenchmarkLike_QueueWorkerPool -benchtime=2s -cpuprofile=cpu.out`
2) Просмотр:  
`go tool pprof -http=:0 cpu.out`
3) Что смотреть: вкладки **Top** и **Flame Graph**; в Top сравните `flat` (время внутри функции) и `cum` (время + вложенные вызовы). Найдите 2–3 самых “дорогих” функции.

**Профиль памяти (по желанию):**
1) Запуск (пример):  
`go test ./... -run=^$ -bench=BenchmarkLike_QueueWorkerPool -benchtime=2s -memprofile=mem.out`
2) Просмотр:  
`go tool pprof -http=:0 mem.out`
3) Что смотреть: **Top/Flame Graph** по аллокациям — где создаётся больше всего объектов/байт.

## 7. Архитектурные требования (важно)

1. `LikeCommand` не должен зависеть от HTTP (никаких `*gin.Context` внутри).
2. Хендлер не должен работать с `chan` напрямую: постановка команды выполняется через отдельный слой/метод.
3. Выполнение лайка (бизнес-операция) отделено от доставки команды: воркер вызывает `ApplyLike(...)`.
4. Время жизни горутин контролируется: `Start/Stop` обязателен.

## 8. Критерии приёмки

1. Эндпойнты Спринта 1 продолжают работать, **новых эндпойнтов нет**.
2. `POST /api/v1/posts/{id}/like` обрабатывает лайки через bounded очередь + worker pool.
3. Повторный лайк тем же пользователем не меняет состояние.
4. `go test ./...` и `go test -race ./...` проходят.
5. Есть unit-тесты на конкурентность.
